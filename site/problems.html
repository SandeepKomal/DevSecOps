Secrets

gitleaks: AWS access key found in history

gitleaks

The error

RuleID:      aws-access-token
...
WRN leaks found: 1

What it means

An access key (AKIA...) was committed. Once pushed, anyone who cloned, forked or viewed the repository may have it.

Confirm it

gitleaks git -v
aws iam list-access-keys --user-name <user>
aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=<key>

Fix it

  1. Rotate first: create a new key if one is still needed, deactivate and later delete the leaked one.
  2. Check CloudTrail for use of the leaked key.
  3. Remove it from code; load credentials from a role or secret store.
  4. Purge history: git filter-repo --replace-text replace.txt --force, re-add origin, push --force, and ask collaborators to re-clone.

Prevent it

Pre-commit gitleaks, push protection, and roles or OIDC instead of keys.

Practise it: AWS key committed, Incident: leaked key used by an attacker · Open in the site

.env file committed

git

The error

	new file:   .env

What it means

.env was not ignored, or was added before it was ignored. .gitignore does not untrack files git already tracks.

Confirm it

git ls-files .env
git log --stat -- .env

Fix it

  1. Rotate every value in it.
  2. git rm --cached .env and add .env to .gitignore.
  3. git filter-repo --path .env --invert-paths --force; push --force.

Prevent it

A template file (.env.example) with no values; gitleaks in pre-commit.

Practise it: .env committed · Open in the site

GH013: Repository rule violations found (push protection)

git push

The error

remote: error: GH013: Repository rule violations found for refs/heads/main.
...
 ! [remote rejected] main -> main (push declined due to repository rule violations)

What it means

GitHub's push protection found a secret in one of the commits you are pushing, not only the last one.

Confirm it

git log -p origin/main..HEAD | grep -n <part of the secret>

Fix it

  1. If it is in the last commit: remove it, git commit -a --amend, push.
  2. If older: git rebase -i to edit that commit, or git reset --soft origin/main and recommit.
  3. Do not use the bypass URL for a real secret.

Prevent it

Keep secrets in the environment or a secret store from the first line of a script.

Practise it: Push blocked by push protection · Open in the site

trivy: secret found in an image layer

The error

CRITICAL: ... (secrets)
 /etc/pip.conf:2 (added by 'COPY pip.conf /etc/pip.conf')

What it means

A file with a credential was copied into the image. Deleting it in a later RUN does not remove it from the earlier layer.

Confirm it

docker history --no-trunc <image>

Fix it

  1. Use RUN --mount=type=secret,id=<id> for the step that needs it, and docker build --secret id=<id>,env=VAR.
  2. Rotate the credential: every pulled copy of the image has it.

Prevent it

.dockerignore for credential files; image secret scanning in CI.

Passwords in terraform.tfstate

gitleaks, Terraform

The error

RuleID:      generic-api-key
File:        terraform/terraform.tfstate

What it means

Terraform state stores every attribute in plain text, including passwords set from variables. A local state file was committed.

Confirm it

git ls-files '*.tfstate*'
grep -n password terraform/terraform.tfstate

Fix it

  1. Rotate the secrets it holds.
  2. Move state to an encrypted, access-controlled backend (backend "s3" with encrypt = true and locking).
  3. git rm --cached the state file, add *.tfstate* to .gitignore, purge it from history.

Prevent it

A remote backend from day one; managed passwords (manage_master_user_password) so state never holds them.

What it means

A dependency version has a known advisory, and a release with the fix exists.

Confirm it

The error

(a finding you have proven cannot be exploited)

What it means

Rules match patterns, not intent: an identifier from a fixed allowlist, a test fixture, an example key.

Confirm it

Trace the input to the flagged line and write down why it is safe.

Fix it

  1. Suppress one rule on one line, with the reason above it: # nosemgrep: <rule-id>, #checkov:skip=<ID>:<reason>, a .trivyignore.yaml entry with statement.

Prevent it

The error

policy: sbom: required, but the image has no CycloneDX attestation

What it means

No SBOM generated, or not attached to the image.

Confirm it

cosign tree <image>
cosign verify-attestation --type cyclonedx ... <image>

Fix it

  1. syft <image> -o cyclonedx-json=sbom.cdx.json, then cosign attest --type cyclonedx --predicate sbom.cdx.json <image>.

Prevent it

SBOM and attestation as required CI steps.

Commits reach main without review

GitHub, Scorecard

The error

| 0 / 10  | Branch-Protection      | branch protection not enabled on development/release branches |

What it means

Branch protection was relaxed: no required reviews, admins exempt (enforce_admins false) or force pushes allowed.

Confirm it

gh api repos/<owner>/<repo>/branches/main/protection
git log --oneline origin/main

Fix it

  1. Revert unreviewed changes with git revert, keeping the record.
  2. Restore the policy: gh api -X PUT repos/<owner>/<repo>/branches/main/protection --input branch-protection.json, with enforce_admins true.

Prevent it

Keep the policy in code and alert on changes to it (audit log, rulesets).

A tag was re-pushed and the cluster runs different code

Kyverno, registry

The error

verifyImages:
  - imageReferences: ["ghcr.io/fernleaf/*"]
    mutateDigest: false
    verifyDigest: false

What it means

Tags are mutable pointers. Without digest pinning, a restart pulls whatever the tag points to now.

Confirm it

kubectl get pods -o jsonpath='{.items[*].status.containerStatuses[*].imageID}'
cosign triangulate <image>

Fix it

  1. Deploy by digest or by an immutable per-commit tag.
  2. Keep Kyverno's verifyDigest and mutateDigest on (both default to true).

Prevent it

Immutable tags where the registry supports them (ECR IMMUTABLE).

Leaked key already used by an attacker

aws, CloudTrail

The error

"EventName": "CreateUser", ... "SourceIPAddress": "203.0.113.77"

What it means

The key was found and used; attackers create persistence early.

Confirm it

aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=<key>
aws cloudtrail lookup-events --region <other-region> ...

Fix it

  1. Deactivate the key.
  2. Remove what it created: users, keys, policies, instances, in every region.
  3. Delete the backdoor user: delete its keys, detach its policies, then delete-user.

Prevent it

No long-lived keys; GuardDuty; multi-region CloudTrail.
